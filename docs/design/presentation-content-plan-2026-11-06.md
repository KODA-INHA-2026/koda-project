# 발표 내용·화면 문구·연출 검토안

2026-11-06. 상태: **검토안, 화면 미반영**. 사용자는 현재 버전을 유지한 채 먼저 발표자의 관점에서 내용을 다시 구성하라고 요청했다. 이 문서는 구현 지시나 최종 카피가 아니다.

후속 진행: 위 상태는 이 검토안을 작성한 시점의 기록이다. 이후 사용자가 추가 리서치 후 수정을 요청해 장면 문구·구조도 설명·제3자 검증 과정을 반영했다. 선택한 내용과 실제 확인 결과는 [추가 리서치·반영 기록](toss-research-application-2026-11-06.md)에 구분해 남겼다.

## 무엇을 중심으로 발표하는가

대표님 답변의 핵심은 KODA가 발급한 증빙이 고객사를 거쳐 외부에 제출된 뒤에도 수신자가 출처와 원본 일치 여부를 확인하도록 하는 것이다. 대표님은 원본 발급→전자서명·해시 생성→블록체인 기록→제3자 대조·검증의 구조와 실제 구현 결과를 강조하라고 조언했다.

우리 기술 선택과 구현은 이 방향에 대한 구체적인 답이다. BTC 잔고 증명서, Ethereum의 문서 등록 계약, SHA-256·EIP-712와 조회 방법은 프로젝트에서 구체화한 설계이며 대표님이 해당 스택을 지정했다는 뜻은 아니다.

보관 자료의 추가 기술 의견은 ‘CTO 추가 의견’으로 표시되어 있다. 이 의견은 일반 전자서명에도 TSA를 통한 시점 보증 방식이 있음을 짚고, 블록체인으로 증명할 수 있는 것과 어려운 것을 나누어 기술적 근거를 보완하라고 요구한다. BIP-340·머클 트리·준비금 증명은 리서치 예시이며 이번 구현에 채택한 기술로 소개하지 않는다.

근거: 작업 폴더의 `대표님 자문 - 방향과 와이블록체인.md`, ‘대표님과 COO님 답변’ 및 ‘KODA CTO 추가 의견’ 부분. 앞에 실린 과거 통합금고·USDC 제안은 현재 과제 범위와 구분한다.

## 발표자가 먼저 잡을 이야기

> 고객사는 KODA가 발급한 증명서를 은행이나 감사인 등에게 제출합니다. 수신자는 이 문서가 KODA에서 발급됐는지, 발급 원본과 같은지 확인할 필요가 있습니다. 저희는 발급 문서의 검증정보를 Ethereum에 기록하고, 제3자가 제출받은 PDF를 그 기록과 직접 대조하는 과정을 구현했습니다.

이 문장은 발표 도입 초안이다. 발표 화면은 이 문장을 전부 자막처럼 옮기지 않고, 증명서가 전달되는 상황과 검증할 세 질문을 보여준다. 기술 장면에서는 알고리즘·입력·처리·출력을 명확히 드러낸다. 제3자 화면 옆에서도 실제 기술 처리가 계속 이어진다.

공식 원칙과 우리 적용 판단을 구분한다. 토스 색상이나 특정 화면을 복제하는 작업이 아니며 KODA의 초록·민트를 유지한다. 이번에는 기존 리서치의 핵심 자료를 현재 문구와 다시 대조했다. 참고 자료 수를 늘리는 것을 개선 성과로 삼지 않는다.

- DFY `ESSENTIAL_04_Grid.fig`: 고정 구조도와 현재 장면의 정렬, 화면 크기별 배치를 검토할 자료.

파일은 `local-design/강의자료/`에 있다. 현재 확인 범위는 파일 존재, 메타데이터, 보존 썸네일이며 전체 강의나 상세 프레임의 원칙을 학습했다고 주장하지 않는다. 특히 작은 썸네일로 정확한 타이포 수치를 추정하지 않는다. 다음 화면 설계 때 관련 프레임을 실제로 열어 적용 근거를 보강할 항목이다. 강의 원본·유료 에셋은 공개 산출물에 포함하지 않는다.

## 장면별 내용과 전달 방법

화면 수와 순서는 현 8개 장면을 검토의 틀로 사용한다. 아래 제목은 모두 후보이며 기존 합의의 세 확인 문구를 임의로 없애지 않는다.

| 장면 | 청중이 이해할 내용 | 화면에서 보여줄 정보·동작 | 문구 후보와 발표자의 보충 |
| --- | --- | --- | --- |
| 1. 전체 흐름 | 외부에 제출된 KODA 증빙을 제3자가 확인한다. | KODA→고객사→제3자의 문서 전달, 출처·원본 일치·변경 여부라는 세 질문. Ethereum은 검증정보의 기록·조회 경로로 연결한다. | 제목 후보: **제출받은 증명서를 발급 원본과 대조합니다.** 발표자는 대표님 답변의 업무 상황과 우리 구현 범위를 먼저 설명한다. |
| 2. 증명서 | 어느 법인의 어느 시점 잔고를 증명하는 PDF가 기준 원본인지 안다. | BTC 잔고 증명서와 잔고 기준시점·발급시각. 같은 원본 객체를 이후 장면까지 이어간다. | **KODA가 BTC 잔고 증명서를 발급합니다.** 발표자는 기존 발급 업무에 검증 기능을 더하는 것이며 실제 KODA 양식은 아닌 가상 사례임을 말한다. |
| 3. 해시 | 제출본과 원본을 파일 전체 바이트로 비교한다. | PDF 전체 바이트→`SHA-256`→32바이트 원본 해시. 이후 장면에서도 같은 해시에 같은 표식을 사용한다. | **원본 PDF의 해시를 계산합니다.** 기술명과 실제 값을 함께 보여준다. 발표자는 해시가 암호화된 PDF나 잔고 자체의 증명이 아님을 설명한다. |
| 4. 서명 | 누가 어떤 문서 정보에 서명했는지 확인할 근거를 만든다. | 문서 ID·해시·발급시각, `EIP-712` domain, 발급자 키→서명. 주소 복구가 무엇을 확인하는지 연결한다. | **발급자가 문서 검증정보에 서명합니다.** 서명과 등록 거래의 차이, 시험 발급키와 공식 KODA 신원의 차이는 발표자 설명·실행 정보에서 분명히 한다. |
| 5. 등록 | 계약이 등록 요청을 검사하고 제3자가 읽을 기록을 남긴다. | KODA→Ethereum 이동, `register(...)`, 발급 권한·서명·중복 ID 검사, `records[documentId]`에 저장되는 값. | **검증정보를 Ethereum에 등록합니다.** 계약에 넣은 규칙과 Ethereum이 제공하는 공개 실행·조회 기반을 구분한다. |
| 6. 확정 | 거래 제출·블록 포함·최종 확정은 다르다. | 실제 등록 거래가 포함된 블록과 영수증, 조회한 `finalized` 기준. 개념 블록 그림과 실측값을 구분한다. | **등록 거래가 확정됐는지 확인합니다.** 표시한 시간이나 재생 애니메이션이 확정의 근거가 되지 않도록 한다. |
| 7. 제출과 검증 준비 | 고객사는 원본을 보관·제출하고 제3자는 해당 문서의 기준을 준비한다. | 고객사→제3자의 PDF, 별도 검증 입력인 문서 ID·서명·신뢰할 발급자/계약. 현재 데모는 이 정보를 미리 불러온다는 표시. | **고객사가 증명서를 제출합니다.** 실제 전달 채널·자동 ID 탐색·외부 패키지를 구현한 듯 연출하지 않는다. |
| 8. 제3자 검증 | 현재 제출본을 원본의 등록 기록과 대조한다. | 이 장면만 제품 UI. 파일 선택·검증·결과 옆에서 로컬 해시/서명자 복구↔확정된 기록 조회→대조가 이어진다. 원본·변경본을 같은 등록 기준에 비교한다. | 제품 버튼 후보: **문서 검증하기**. 기술 처리 영역은 `SHA-256`, `ECDSA`, `JSON-RPC / eth_call`, `finalized`를 정확히 표시한다. 결과는 발급 출처·원본 일치·현재 제출본의 변경 여부로 설명한다. |

세부 호출 순서를 새로 꾸미지 않는다. 실제 구현에는 검증 시작 전 계약 배포·신뢰 기준 확인도 있다. 연출에서 묶어 보여주는 처리 단계와 실제 호출 로그를 대조한 뒤 구현해야 한다.

## 현재 문구를 어떻게 다시 쓸 것인가

단어를 무조건 짧게 줄이거나 영어를 모두 번역하는 작업이 아니다. 같은 말도 구조도 제목, 기술 동작, 제3자 버튼, 발표 대본에서 필요한 정보량이 다르다.

| 현재 표현 | 문제 | 후보 또는 배치 방향 |
| --- | --- | --- |
| 공개 검증 인프라 | 문서와의 관계가 없는 추상적 분류명이다. | 구조도 제목은 **Ethereum**으로 두고 역할을 **KODA가 발급한 문서의 검증정보를 기록합니다**로 설명한다. 두 표현을 중복된 제목으로 쌓지 않는다. |
| 고객 BTC가 올라가는 체인이 아님 | 설계 중의 오해 방지 메모가 본문이 됐다. | 이 문장을 그대로 대체하기보다 Ethereum의 역할 설명으로 통합한다. BTC는 증명서의 자산 항목에서 설명한다. |
| 업무 주체와 공개 검증기록의 연결 | 추상 명사가 겹치고 청중의 행동이 보이지 않는다. | 전체 상태에서는 **증명서 발급부터 제3자 검증까지**. 각 장면에서는 실제 진행 중인 행동을 표시한다. |
| 독립 대조 | 현업에서 무엇을 하는지 바로 읽히지 않는다. | 주체 칸에는 **제출 문서 검증**. 독립성의 의미는 별도로 신뢰 기준과 조회 경로로 설명한다. |
| 공개된 검증 기준을 연결합니다 | 무엇을 어디에 연결하는지 알기 어렵다. | **문서 검증정보를 기록하고, 제출된 PDF와 대조합니다.** |
| 어느 발급키의 기록인지 서명으로 연결합니다 | 키·기록·연결의 관계가 모호하다. | **발급자가 문서 검증정보에 서명합니다.** |
| 원본은 고객사에, 검증 기준은 체인에 | 리듬은 있으나 무엇을 보관하고 제출하는지 생략된다. | 전달 장면 제목은 **고객사가 증명서를 제출합니다**. 고객사 보관 PDF와 Ethereum 기록은 그림의 위치로 드러낸다. |
| 공개 체인에서 대조하기 | 제품 사용자의 목적보다 처리 수단이 버튼에 먼저 나온다. | 제품 버튼은 **문서 검증하기**. 인접 기술 영역에서 제출 PDF와 Ethereum 등록값을 대조함을 보여준다. |
| 버튼 뒤에서 일어나는 일 | 화면의 버튼을 설명하는 메타 문장이다. | 영역 제목은 **검증 과정**. 내부 단계의 동사와 기술명으로 실제 처리를 보여준다. |
| 원본 기준과 차이 | 무엇의 차이인지 모호하다. | 질문은 **이후 변경되지 않았는지**를 유지하되, 판정 설명에 **현재 제출본과 발급 원본을 비교한 결과**를 명시한다. 모든 변경 이력의 증명으로 쓰지 않는다. |

위 후보도 확정 전 소리 내어 읽어야 한다. 기술자에게 정확하고 청중에게 자연스러운지, 그림과 함께 읽을 때 같은 내용을 반복하는지 확인한다. 현재 첫 화면의 ‘발급한 문서를, 제3자가 직접 확인합니다’처럼 이미 기능을 전달하는 문구는 일괄 교체하지 않는다.

## 앞선 기술 피드백과 함께 지킬 것

- 발급서명 복구와 허용 발급자 확인을 기본 흐름에서 보이게 한다. 전체 해시와 호출 로그는 목적에 맞게 읽을 수 있어야 한다.
- 사전 로드한 검증정보라는 현재 조건을 분명히 한다. 임의 PDF 자동 탐색이나 외부 패키지는 구현된 기능이 아니다.
- 원본 일치와 현재 제출본 변경 여부는 같은 해시 대조의 두 표현이다. 세 가지 사용자 질문과 기술 검사의 개수를 혼동하지 않는다.
- 등록·조회 두 방향 모두에서 Ethereum을 보여준다. 제3자 UI가 나와도 기술 설명을 끊지 않는다.
- 번호 중복·작은 지도 글씨·초기 복원 중 회사명이 바뀌는 문제는 별도의 구현 점검 항목으로 유지한다.
- 기존 실제 등록 PDF의 회사명을 화면만 바꿔 위조하지 않는다. 인하테크홀딩스 신규 사례에는 새 서명·등록이 필요하다.

## 적용 전 검토 기준

발표자가 각 장면을 보고 한 문장으로 목적을 설명할 수 있어야 한다. 청중은 주체·입력·처리·결과와 다음 단계의 관계를 화면에서 찾을 수 있어야 한다. 기술 용어가 존재하는지만 점검하지 않고 **그 기술이 어떤 검사에 쓰였는지** 확인한다. 이 문서의 문구·배치·연출은 아직 제품에 적용하거나 사용성 검증한 결과가 아니다.

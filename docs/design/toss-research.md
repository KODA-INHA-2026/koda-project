# KODA 문서 검증 실증 — Toss 원칙 리서치와 적용 메모

> 작성일: 2026-11-06\
> 범위: 공개된 Toss 1차 자료를 바탕으로 한 **원칙 참고**다. Toss의 브랜드·UI·에셋·TDS를 복제하거나 Toss의 승인·후원을 뜻하지 않는다.\
> 고정 전제: KODA의 그린·민트·소프트 뉴트럴 색 정체성은 유지한다. Toss 특유의 파랑/검정 팔레트로 바꾸지 않는다.

## 1. 결론: 현재 데모가 가져가야 할 모습

KODA 데모는 "블록체인을 이용한 대시보드"가 아니라, **실제 증명 이벤트가 제3자의 독립 검증으로 이어지는 한 편의 처리 기록**이어야 한다.

- **처리 구간**은 제품 UI처럼 만들지 않는다. KODA와 고객사, PDF와 체인 사이에서 실제로 일어나는 일을 한 장면씩 보여주는 *기술 캔버스*다.
- **검증 구간**만 제품 UI다. 제3자는 PDF를 고르고 `공개 체인에서 대조하기`를 누른 뒤, 사람이 읽을 수 있는 결론과 필요한 증거만 본다.
- 각 장면은 하나의 질문을 중심축으로 삼는다. 이는 기술 정보를 줄이라는 뜻이 아니라, `입력 → 실제 연산/검사 → 출력 → 다음 단계 의존성`을 한 번에 읽히게 하라는 뜻이다. 전체 흐름은 `무엇을 고정했나 → 무엇을 해시했나 → 누가 무엇에 서명했나 → 컨트랙트가 무엇을 검사했나 → 포함과 확정은 어떻게 다른가 → 제3자가 어떤 공개 기록을 다시 읽나`다.
- 화면 속 모션은 실제 사건을 설명한다. 꾸며진 로딩·순환 애니메이션·근거 없는 숫자 변화는 쓰지 않는다.

이는 Toss가 말하는 한 화면의 핵심 메시지, 정보가 필요한 순간의 단계적 제공, 실제 정보로 대기 시간을 설명하는 원칙을 KODA의 기술 실증에 적용한 것이다. 아래의 "KODA 적용"은 우리 해석이며 Toss의 공식 규칙 자체는 아니다.

## 2. 조사 범위와 신뢰도

### 이번 보정에서 바로잡는 해석

공식 Toss 자료는 복잡한 정보를 **읽는 순서와 구조**로 설계하는 사례를 보여주지만, "기술 용어·원시 데이터는 기본 화면에서 제거하라"고 말하지 않는다. 특히 디자인 시스템 가이드 글은 큰 구조부터 상세 스펙으로 이어지는 점층적 구성을 설명한다. 따라서 KODA에서는 정확한 기술명과 관련 값이 해당 장면에서 계속 보여야 한다. 평이한 한국어 문장은 그 값을 *대신하는 번역*이 아니라, 값의 역할·한계·다음 의존성을 설명하는 보조 레이어다.

## 3. `Presentation.tsx`에 적용할 구체적 변경 방향

대상: `apps/web/src/live/Presentation.tsx` 및 대응 CSS. 이 문서는 방향 기록이며 여기서는 프론트엔드를 수정하지 않는다.

### A. 정보 위계: 장면 하나 = 증명 질문 하나, 기술값은 해당 장면에 남김

현재 `intro → pdf → hash → sign → contract → block → handoff → verify`의 시퀀스는 옳다. 개선은 **각 화면의 읽기 밀도**다.

1. **첫 시선에는 제목 하나와 한 줄의 사실을 둔다.**
   - 이것은 발표자가 장면의 질문을 잡게 하는 장치다. 동시에 해당 장면의 증거 객체에는 필수 기술값을 계속 표시한다.
   - PDF: `어느 시점의 잔고인지 문서에 고정해요` / `잔고 기준시점과 발급시각은 다릅니다.`
   - Hash: `파일 전체를 하나의 지문으로 바꿔요` / `글자 하나가 달라도 지문이 달라져요.`
   - Sign: `KODA 발급자가 이 기준에 서명해요` / `서명은 아직 체인 등록이 아닙니다.`
   - Contract: `컨트랙트가 등록 조건을 확인해요` / `발급자·서명·첫 등록만 통과합니다.`
   - Block: `블록 포함과 최종 확정은 달라요` / `확정된 기록만 제3자가 판정에 사용합니다.`

2. **식별자와 기술 용어는 해당 연산의 증거 객체 안에서 항상 보인다.**
   - `SHA-256`, `EIP-712 / ECDSA secp256k1`, `msg.sender`, `register(...)`, `records[documentId]`, receipt block, finalized block, `eth_call`은 해당 장면의 주된 증거다. 제목 아래의 설명 문장과 분리된 모노스페이스/필드 형태로 명확하게 배치한다.
   - 전 장면에 모든 값을 반복 나열하지 않는다. 단, 한 번도 숨기지 않는다. 값은 **그 값이 입력·검사·출력으로 작동하는 장면**에서 보이며, 다음 장면에는 의존성 연결선과 필요한 참조값으로 이어진다.
   - 전체 해시·주소는 relevant scene에서 줄바꿈 가능한 전체 문자열과 복사 수단을 제공한다. 제목·actor rail·반복 라벨처럼 좁은 공간에서는 축약값을 쓰되, 축약이 유일한 노출이 되어서는 안 된다.

3. **하단 전송 컨트롤은 발표 제어라는 성격을 숨기지 않는다.**
   - `실제 실행 기록 재생`이라는 현재 라벨은 유지한다.
   - 일반 사용자의 업무 UI처럼 보이지 않도록, 인디케이터는 작고 차분하게 유지한다.
   - `직접 검증하기`만 명시적인 핸드오프 CTA로 둔다. 다른 장면에는 CTA를 추가하지 않는다.

### B. 기술 캔버스와 제3자 앱의 대비

#### 1) `intro`부터 `handoff`까지: 기술 캔버스

- 배경: 기존 KODA의 아주 옅은 민트/뉴트럴을 유지한다. 큰 흰 카드 3~4개를 매 장면마다 띄우지 않는다.
- 객체: PDF 종이, 바이트 흐름, 서명 필드, 컨트랙트 규칙, 블록 노드처럼 **해당 단계의 단 하나의 물리적/논리적 객체**를 화면 중앙에 둔다.
- 연결: 선은 "데이터가 이동했다"가 아니라 "어떤 사실이 다음 기준을 만들었다"는 인과만 표현한다. 화살표가 계속 흐르거나 파티클이 순환하지 않는다.
- 행위자: 상단의 `KODA · 고객사 · 제3자` rail은 작은 처리 위치 표식이다. 카드형 조직도처럼 키우지 않는다.
- 라벨: `가상 사례`, `실제 실행 기록`, `실시간 조회`를 동적 상태 가까이에 텍스트로 표시한다. 예시 숫자(100 BTC)가 실거래 정보처럼 오해되지 않게 한다. 이미 등록된 과거 실행 기록의 PDF 고객명은 역사적 증거이므로 그대로 보존하며, 향후 새 문서에 쓸 가상 고객명은 별도 승인 전까지 바꾸지 않는다.

#### 2) `verify`만: 제3자 제품 UI

- 더 밝은 표면과 명확한 입력/결과 구조로 전환한다. 이때도 KODA 그린·민트만 사용하고 색보다 제목·아이콘·텍스트로 상태를 설명한다.
- 기본 상태는 `검증할 PDF를 선택해 주세요.` 하나의 요청과, 샘플 2개/파일 선택 중 하나의 명확한 조작만 둔다.
- 주요 CTA는 `공개 체인에서 대조하기`. `public RPC`, `finalized`, `EIP-712`은 버튼 문구에 쓰지 않는다.
- 결과는 차트가 아니라 **문장 우선**이다.
  - 일치: `문서 원본과 체인 기록이 같아요.`
  - 파일 불일치: `제출한 파일이 발급 원본과 달라요.`
  - finality 대기: `블록에 기록됐어요. 최종 확정을 기다리고 있어요.`
  - RPC 실패: `지금 체인 기록을 불러오지 못했어요. 다시 시도해 주세요.`
- `대조한 기술 정보`는 현재 `details`처럼 접을 수 있어야 한다. `H파일 = H서명 = H체인`의 관계가 한눈에 보이되, 해시 전문은 기본 화면을 압도하지 않는다.

### C. 아이콘: 의미를 보강하고, 독자적 스타일로 유지

현재 인라인 선 아이콘은 한 스타일로 정리되어 있어 유지할 가치가 있다. 아래처럼 의미를 고정한다.

| 의미 | 제안 아이콘 | 사용 위치 | 금지 |
|---|---|---|---|
| 문서 원본 | file | PDF 단계, 파일 선택 | 장식용 파일 반복 |
| 파일 지문 | fingerprint 또는 작은 32-byte grid | Hash 단계 | 자물쇠로 대체 |
| 발급자 확인 | shield-check | 서명/검증 결과 | `공식 KODA 인증`처럼 오해하게 하기 |
| 체인 등록 | link 또는 blocks | 계약/트랜잭션 | 무한 체인 애니메이션 |
| 완료 | check | finality 이후, 일치 결과 | 포함 단계에서 완료 체크 사용 |
| 주의/불일치 | alert-circle | 파일 불일치/RPC 실패 | 빨강만으로 오류 전달 |

아이콘은 클릭 가능성을 대신하지 않는다. 버튼에는 텍스트를 병기하고, 아이콘만 있는 이전·다음·재생 버튼은 `aria-label`로 기능을 설명한다. 이것은 Toss TDS 글의 "모양이 아니라 기능을 설명하는 대체 텍스트" 원칙과 맞닿는다.

### D. 모션 명세: 장면 전환이 아니라 증거의 변화

Toss의 공식 원칙은 "모션을 공통 언어와 토큰으로 명세"하는 데 있다. 아래 시간값·이름은 **KODA 구현 제안**이다.

| token (KODA 제안) | 발생 조건 | 보여줄 변화 | 제한 |
|---|---|---|---|
| `evidence-enter` | 장면 진입 | 제목→객체 순서로 짧게 나타남 | 한 객체에 한 모션만 |
| `evidence-transform` | PDF→hash, 서명→등록 | 이전 증거가 다음 증거의 원인이 되는 1회 전환 | 반복·역재생 금지 |
| `chain-included` | receipt block 확인 | tx 노드가 특정 블록에 자리 잡음 | checkmark 사용 금지 |
| `chain-finalized` | finalized height 조건 충족 | 해당 블록이 안정 상태로 바뀜 | 실제 조건 전 미리 재생 금지 |
| `verification-result` | 브라우저 해시+서명+체인 read 종료 | 결과 문장과 3개 비교 상태가 함께 나타남 | 단독 색상/아이콘만으로 전달 금지 |

- `prefers-reduced-motion`에서는 변화 없이 현재 단계와 결과를 즉시 표시한다.
- recorded mode에서는 이미 발생한 사건을 재생하는 것이므로 `과거 실제 실행 기록`이라고 밝힌다. live mode에서는 RPC가 실제로 확인한 상태만 표시한다.
- `included`와 `finalized`를 한 프레임·한 제목·한 완료 아이콘으로 합치지 않는다. 이 구분 자체가 KODA 기술 가치의 핵심이다.

### E. 화면별 연출 스토리보드

1. **Intro — KODA 발급 문서는 어떻게 제3자가 확인할까**\
   **Actor/경계:** KODA(기존 증명 발급) → 고객사(원본 보관·제출) → 제3자(대조)라는 세 역할을 먼저 놓는다.\
   **보여줄 사실:** KODA가 BTC 잔고 증명서를 발급하는 기존 업무 위에, `hash → sign → register → query → compare`라는 구현된 검증 경로를 연결한다. 첫 장면에서 BTC와 Ethereum을 동등한 자산 선택지나 두 개의 고객 자산 체인으로 비교하지 않는다. 전체 흐름을 보여줄 때 Ethereum은 `DocumentRegistry`의 **등록·조회 인프라**로 표시할 수 있고, BTC는 이후 PDF의 고객 수탁 자산 예시로만 나타낸다.\
   **모션:** PDF가 KODA에서 고객사 보관 영역으로 이동하고, 같은 PDF의 윤곽이 후속 기술 경로의 시작점으로 남는다. 기술 상세를 지우지 말고 다음 장면들에서 어떤 처리가 실제로 실행되는지 예고한다.

2. **PDF — 원본 확정**\
   **입력/Actor:** KODA가 발급한 최종 PDF 바이트. 고객사는 이 원본을 보관한다.\
   **필수 표시:** `BTC 잔고 증명서`, 법인명, `잔고 기준시점`, `발급시각`, `KODA 수탁 BTC 전체 잔고`, 최종 PDF byte size. BTC는 여기서만 고객 수탁 자산의 가상 사례로 보인다.\
   **기록 경계:** PDF 원문·고객 정보·BTC 수량은 체인에 기록하지 않는다. 이미 등록된 과거 실행 기록은 PDF에 적힌 **한울테크홀딩스㈜** 명칭을 그대로 보존한다. 향후 새 증명서의 **인하테크홀딩스㈜** 적용은 사용자 승인 후 별도 발급이며, 재생 기록의 이름을 교체할 근거가 아니다.

3. **Hash — SHA-256 비교 기준 생성**\
   **입력:** 2단계의 정확한 PDF 전체 바이트.\
   **실제 연산:** 브라우저가 `SHA-256(PDF bytes)`를 계산한다.\
   **필수 표시:** `documentHash` 전체 32-byte/0x 문자열, byte stream → digest의 시각 연결, "글자 하나가 달라도 해시가 달라진다"는 역할 설명.\
   **출력/의존성:** 이 해시가 다음 EIP-712 typed data의 `documentHash` 필드로 선으로 이어진다. 여기서 지문이라는 비유는 해시를 대체하지 않으며, PDF 원문이 온체인에 올라가지 않는다는 경계만 설명한다.

4. **Sign — EIP-712 구조화 데이터와 ECDSA 서명**\
   **입력:** `documentId`, 3단계의 `documentHash`, `issuedAt`, EIP-712 domain, 시험 발급자 EOA.\
   **실제 연산:** 브라우저/MetaMask가 typed data에 ECDSA secp256k1 서명을 생성한다.\
   **필수 표시:** 세 message 필드와 domain, 발급자 주소, signature 전문 또는 복사 가능한 전문, `recover(signature) → issuer`라는 검증 관계. `시험 발급자 ≠ 공식 KODA 신원 인증` 경계를 붙인다.\
   **출력/의존성:** 서명은 아직 트랜잭션이 아니며, 5단계 `register(...)` calldata의 입력이 된다는 선을 보여준다.

5. **Contract — Solidity/EVM 등록 조건과 저장값**\
   **Actor/인프라:** KODA 측 시험 발급자가 Ethereum Sepolia의 `DocumentRegistry`를 호출한다. Ethereum은 고객 자산의 위치가 아니라 이 검증정보의 공개 기록 인프라다.\
   **실제 검사:** `msg.sender == authorizedIssuer`, `ECDSA.recover(digest, signature)`, `records[documentId] == empty`를 정확한 코드/수식과 함께 보인다.\
   **출력:** 첫 등록만 허용되면 `records[documentId] = {documentHash, issuedAt}`가 저장되고 이벤트/transaction input으로 이어진다. 서명·ID·hash·issuedAt은 필수 기술값으로 계속 보인다.

6. **Block — 트랜잭션 포함과 finality**\
   **입력:** 실제 `register(...)` transaction hash, contract address, receipt.\
   **실제 상태:** `submitted → included at receipt.blockNumber → current finalized block`을 한 선 위에 분리해 보인다. `included` 노드는 완료가 아니며, `finalized` 조건이 충족될 때만 안정된 기록 표시로 바뀐다.\
   **필수 표시:** tx hash 전문/복사·explorer 링크, receipt block number, 현재 finalized height, 조회 시각. replay는 과거 receipt, live는 현재 RPC 응답이라는 출처 표기를 유지한다.\
   **출력/의존성:** 제3자가 다음 장면에서 동일 컨트랙트를 `eth_call`로 읽을 수 있는 공개 기준이 생긴다.

7. **Handoff — 고객사 제출과 검증정보 연결**\
   **Actor:** 고객사가 원본 PDF를 기존 방식대로 감사인·금융기관 등 제출처에 전달한다. KODA가 새 고객용 앱을 만든다는 주장이 아니다.\
   **보여줄 연결:** 제출 PDF와 `documentId`/등록 tx reference가 제3자 검증 경로로 함께 이동한다. 고객사 보관 PDF는 off-chain, 등록 정보는 Ethereum 공개 조회 대상이라는 두 위치를 같은 다이어그램 안에 명시한다.\
   **의존성:** 제3자는 지갑·가스비 없이 PDF bytes는 로컬에서, 신뢰 기준은 공개 RPC에서 읽게 됨을 다음 장면으로 잇는다.

8. **Verifier — 제3자 제품 UI 안에서도 기술 trace 유지**\
   **UI/Actor:** 이 장면만 제3자를 위한 제품 창이다. 그러나 그 바깥 또는 뒤쪽의 기술 canvas에서 `local SHA-256 → ECDSA recover → JSON-RPC eth_call / finalized read` 경로가 계속 연결되어 보여야 한다.\
   **실제 연산:** 제출 PDF의 `Hfile`을 계산하고, EIP-712 message에 포함되어 서명된 `documentHash`를 `Hsigned`로 읽는다. `recoverTypedDataAddress`는 서명에서 **issuer 주소만** 복구한다. 이어서 `records[documentId]`의 `Hchain`과 finalized 상태를 다시 읽는다.\
   **필수 결과:** `Hfile = Hsigned = Hchain`이면 "발급 원본과 일치", `Hfile ≠ Hsigned = Hchain`이면 "제출한 파일이 발급 원본과 다름"을 보여준다. hash 3개·recover 결과·eth_call 대상·receipt/finalized 값은 세부 창에 숨기는 것이 아니라 검증 UI 주변의 technical trace에 보인다.\
   **범위:** 문서 출처와 발급 원본 대비 동일성만 확인한다. 실제 BTC 보유량, 고객 신원, 취소/현재 유효성, 변경된 특정 필드나 사기 여부를 증명한다고 말하지 않는다.

## 4. 검수 체크리스트

> 이것은 디자인·구현 검토 기준이다. 실제 실행에서 어떤 상태를 재현·캡처했는지는 별도의 QA/검증 기록으로 관리하며, 아래 항목이 모두 이미 실행되었다는 뜻은 아니다.

### 실제성

- [ ] 거래가 포함된 사실과 finality를 별도로 보여주는가?
- [ ] recorded/live, 가상 사례/실시간 결과가 분명히 다르게 표시되는가?
- [ ] PDF 원문·고객 정보·개인키·BTC 잔고가 체인에 올라간다고 암시하지 않는가?
- [ ] 일치는 `발급 원본과의 동일성`이며 BTC 사실성 증명이 아님을 유지하는가?

### 이해 가능성

- [ ] 각 장면은 제목 하나, 보조 문장 하나, 증거 객체 하나를 중심축으로 읽히되, 그 객체의 입력·연산·출력·의존 기술값은 모두 보이는가?
- [ ] `SHA-256`, `EIP-712 / ECDSA secp256k1`, `register(...)`, `finalized`, `eth_call`이 관련 장면에서 정확한 값·관계와 함께 보이고, 한국어 설명은 그 기술을 대체하지 않고 역할을 설명하는가?
- [ ] CTA가 구체적 행동과 대상(`공개 체인에서 대조하기`)을 말하는가?
- [ ] 오류/대기 상태에 상황·이유·다음 행동이 있는가?

### 시각·접근성

- [ ] KODA 그린·민트·소프트 뉴트럴을 유지하고 Toss 색/로고/에셋을 복제하지 않았는가?
- [ ] 색, 아이콘, 문장 중 최소 둘 이상으로 상태를 전달하는가?
- [ ] 해시·주소·긴 한국어 문구가 작은 화면/큰 글씨에서 잘리지 않는가?
- [ ] 아이콘 버튼에 기능을 설명하는 접근성 이름이 있고, 결과 변화가 스크린 리더에 전달되는가?
- [ ] reduced motion에서도 이야기와 검증 기능이 유지되는가?

## 5. 패키지·에셋 경계

- Toss Design System 문서는 Toss 미니앱/내부 제품 환경의 문서다. 본 React 웹 데모가 그 라이브러리·라이선스·지원 범위를 그대로 쓸 수 있다고 가정하지 않는다.
- `toss/slash`는 [2025-12-18 archive](https://github.com/toss/slash)된 저장소다. 신규 의존성으로 추가하지 않는다.
- 현재 CSS와 기존 선형 아이콘을 사용하면 충분하다. 모션을 위해 새 라이브러리를 도입할 필요는 없다.
- 공개 컨퍼런스 PDF·Figma 프레임은 재사용 조건이 불명확할 수 있다. 별도 승인 없이 화면·에셋·브랜드 표현을 복제하지 않는다.

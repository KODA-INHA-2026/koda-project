# 대표님 최종 답변 기준 01·02 검토

사용자는 기술 부록을 피칭용 설명이 아닌 기술 명세·참고문헌으로 개정하고, 데모 01·02에서 더 강조하거나 구현할 점을 물었다. 이번에는 부록과 검토 기록만 변경하며 데모 코드·기술·트랜잭션은 변경하지 않는다.

## 근거와 현재 상태

최우선 근거는 `기업 프로젝트/데모 개발/11.5일 대표님 답변 기준으로 최종결과물/대표님 자문 - 방향과 와이블록체인.md`의 대표님 답변 63–67, 86–90행이다. 같은 파일 115–127행은 CTO 추가 의견이다. 이를 대표님이 기술 하나하나를 지정한 답변으로 합치지 않는다.

- 63–67행: 문서 진위·위변조의 제3자 검증, 세 가지 질문, 원본 발급 → 전자서명·해시 → 블록체인 기록 → 제3자 대조, 내부 관리 정보와 외부 제출 증빙의 정합성 및 실제 구현 결과 강조.
- 86–90행: 내부 시스템 자체의 통제와 별도로, 고객사를 통해 외부로 유통되는 자료의 출처·무결성을 검증하는 수단.
- 118–119행: 일반 전자서명도 TSA 등을 통해 시점 인증을 사용할 수 있으므로, 블록체인의 보장 범위와 기술적 방법을 정확히 설명하라는 CTO 의견.

현재 01은 가상 원본 PDF, SHA-256·서명, Ethereum 등록, 고객사의 PDF·JSON 다운로드를 연결한다. 현재 02는 수신 파일을 직접 입력받아 서명과 실제 등록 정보를 대조한다. `verifier-outcome.ts`에는 대표님의 세 질문이 이미 구현돼 있다. 따라서 새 검증 질문이나 세부 장면을 계속 추가할 필요는 없다.

## 우선 검토할 개선

| 우선순위 | 현재 상태 | 권고 | 구분 |
| --- | --- | --- | --- |
| 1 | `certificate.ts`의 가상값으로 PDF를 생성한다. 별도 수탁 원장 스냅샷은 없다. | 01 안에서 작은 ‘가상 발급 원천정보’가 PDF의 법인·잔고·기준시점으로 이어지는 연결을 보여준다. 구현한다면 동일한 데이터 객체에서 원천정보 표시와 PDF 생성을 파생한다. | 제안하는 데모 보강. 실제 KODA API 연동 요구로 확대하지 않음. |
| 2 | 서명 복구는 실제 실행되지만 기본 장면의 중심은 PDF 해시와 체인 해시 대조다. | 별도 장면 없이 ‘발급서명 확인’과 ‘해당 ID의 등록 원본 대조’를 구분해 짧게 표시한다. 결과의 기존 세 질문은 유지한다. | 이미 구현된 기술의 표현 개선. |
| 3 | 실제 컨트랙트·등록 거래 링크와 trace는 펼침 영역에 있다. | 02의 대조 결과 근처에 ‘기존 등록 거래’와 ‘이번 조회 기준 블록’을 간결하게 제시한다. 사전 등록 근거와 현재 조회를 구분한다. | 대표님이 강조한 실제 구현 결과를 드러내는 개선. 새 지갑 승인 불필요. |
| 4 | 잔고 기준시점·발급 기재시각은 01에 이미 구분돼 있고 02에는 확정 블록이 있다. | 기본 화면은 유지하며 기술 상세에서 등록 블록 시각과 finalized 여부를 분리한다. ‘변경 없음’의 검증 의미는 현재 제출본이 등록 원본과 일치한다는 뜻으로 한정한다. | 정확성 보강. 새로운 TSA 기능 요구가 아님. |

시연용 원천정보 객체를 추가하더라도 그 값이 실제 수탁 원장과 맞다는 사실을 블록체인이 검증하는 것은 아니다. 발급 원본을 해시로 고정한 이후의 출처·무결성이 이번 기술의 직접 검증 범위다. 현재 공개 실증 PDF의 고객사는 한울테크홀딩스㈜로 서명·등록돼 있으므로 기존 원본을 인하테크홀딩스㈜로 바꾸어 같은 기록과 연결하면 안 된다.

`finalizedBlock`은 조회한 확정 블록 번호다. 앱이 정확한 확정 벽시계 시각을 수집하는 것은 아니다. `issuedAt`은 발급자가 기재·서명한 값이고, `receiptBlockTime`은 등록 거래가 포함된 블록의 timestamp다.

## 왜 블록체인인가와 보조 사례

현재 원본·100→120 BTC 변경본은 바이트 무결성을 보여주지만, 이 변경 탐지는 전자서명으로도 가능하다. 팀장이 제안한 ‘같은 ID의 다른 PDF를 신뢰 발급자가 다시 서명한 경우’를 보조 비교로 준비하면, 유효한 서명과 이미 등록된 원본의 일치가 다른 질문임을 드러낼 수 있다.

이 비교는 대표님이 직접 요구한 사례가 아니라 팀의 설명 방법이다. 신뢰 발급자가 대체 문서를 서명했다는 가정을 명시해야 하며, 임의 공격자가 키 없이 KODA 서명을 만들 수 있다는 표현은 틀리다. 현재 이 사례는 구현돼 있지 않고, 실제 서명 사례를 만들려면 사용자의 지갑 승인이 필요하다. 이번 작업에서는 실행하지 않는다.

같은 ID 재등록을 막는 규칙 자체는 중앙 DB에서도 구현할 수 있다. Ethereum의 추가 역할은 발급기관 DB와 분리된 공통 상태, 합의된 기록과 외부 조회 경로다. 현재 단일 RPC 의존은 남는다.

## 이번 데모의 필수로 확대하지 않을 것

- KODA 로그인이 없다는 조건: 대표님은 외부 유통 자료의 검증을 강조했으며 무로그인 서비스를 확정하지 않았다. 02 접근 권한은 KODA와 협의한다.
- 실제 BTC 잔고·소유권·준비금·이중 담보 증명, 통합금고, 머클 트리·ZK: 문서 검증 중심 범위 밖이다. CTO 예시는 채택 지시가 아니다.
- 일괄 마스킹·수신자 권한 운영 전체: 기존 고객사 내부 정책과 제3자 서비스 접근 정책을 구분한다.
- 공식 KODA 키 등록·키 교체·폐기·정정: 실제 도입에 중요하지만 이번 01·02의 필수 신규 기능으로 임의 확정하지 않는다.

## 기술 부록 개정

동일한 저장된 14장 프레젠테이션을 기술 참고용으로 개정했다. SHA-256 계산, EIP-712 digest와 domain, ECDSA/secp256k1 수식, ABI selector와 calldata, 실제 storage slot, 거래·receipt·event 대조, finality, JSON-RPC wire format, 입력 파서와 trust anchor, 최종 성공 조건을 넣었다. 본문에 공식 출처와 고정 소스 위치를 표시하고 발표자 노트 및 원고에는 전체 링크·추가 기술적 주석을 남긴다.

원고: `docs/presentation/technical-reference-2026-11-06.md`. 표준·코드 대조와 전 장 렌더링으로 검토하며 앱 코드는 변경하지 않으므로 앱 회귀 검사를 새로 실행했다고 주장하지 않는다.

# 설명 문서와 KODA 자료에 맞춘 데모 개선

2026-11-08 작업. 아래 로컬 개선·검증을 마친 뒤 사용자의 요청으로 같은 날 GitHub Pages에 게시했다.

## 사용자의 문제의식과 기준

기호님이 직접 이해하며 정리한 `쉬운 언어로 설명.md`를 데모 내용의 현재 기준으로 삼았다. KODA가 제공한 PDF·답변·서면 의견·검토의견을 함께 대조하며, KODA가 확인한 사실 / 우리가 제안한 구성 / 실제 구현 결과를 구분한다. 사용자가 작성한 설명 문서와 Notion은 수정하지 않았다.

핵심 원칙은 사용자가 다시 명시한 여덟 가지다.

1. 대표님과 팀의 방향을 유지하고 미확정 내용을 실제 기능으로 넣지 않는다.
2. 디자인은 내용 전달 수단이다. 정보 배치·표현은 기존 토스 리서치를 참고하고 KODA 색을 유지한다.
3. KODA·고객사·제3자의 역할, 처리 장소와 동작을 구분한다.
4. 서비스 UI는 제3자 화면에만 두고 앞 단계는 처리 과정으로 보여준다.
5. 검증에서도 Ethereum 조회 → 응답 → PDF 대조를 보여준다.
6. 기술 이름 나열보다 동작과 결과를 보여주며 설명을 빠르게 없애지 않는다.
7. 01–03은 짧게, 04는 핵심으로 유지한다. 기술 상세·가정·재생·실행을 구분한다.
8. 기존에 잘된 장면을 무너뜨리지 않는다.

근거: `기업 프로젝트/데모 개발/11.5일 대표님 답변 기준으로 최종결과물/대표님 자문 - 방향과 와이블록체인.md`의 대표님 답변(63–90행), CTO 의견(118–119행), 11월 7일 검토의견과 대표님 추가 답변. 여기서 제시한 증빙의 중요성, 네 단계 구조, 제3자의 원본 대조, 대안 비교와 증명 범위를 기준으로 삼았다. Ethereum·등록 규칙·브라우저 처리·MetaMask는 팀의 구현 선택이다.

## 이번에 반영한 부분

- 01: 외부 감사 제출 상황, 기준시점의 수탁정보 → PDF 원본. 고객사의 요청 화면과 KODA 내부 처리를 혼동하지 않도록 실제 브라우저 구현과 제안 서버 구성을 구분했다.
- 02: 브라우저의 Web Crypto/SHA-256 → EIP-712 서명 요청 → 시험 발급자의 MetaMask 서명. 기술 이름을 처리 장소처럼 쓰지 않고 각 처리와 결과를 연결했다.
- 03: DocumentRegistry를 표준 기술처럼 보이는 주표현에서 빼고 ‘등록·조회 컨트랙트’로 설명한다. 우리가 작성한 발급자·서명 확인과 같은 문서 ID 재등록 거부 규칙, PDF/JSON의 고객사 전달을 표시했다. 블록 포함과 최종 확정은 구분한다.
- 04: 원본·PDF 변경본·재서명본 모두 같은 위치에 로컬 서명 검사와 PDF↔서명정보 대조 결과가 남는다. Ethereum 응답과 등록 원본 대조는 기존 연속 동작을 유지한다. ‘변경 없음’은 현재 파일의 원본 일치 의미로 좁혔다.
- Why Blockchain: 서버에서도 원본 대조·재서명 비교가 가능함을 명시하고, 공개 네트워크에 두는 등록 규칙과 발급기관 밖 공통 기준이라는 추가 가치를 별도로 설명한다. 자세한 비교는 펼쳐 보는 영역에 두었다.
- 05: 이전 Node.js 실제 실행 기록을 보여주는 화면임을 명확히 했다. 현재 브라우저에서 Node.js를 새로 실행한 것처럼 표현하지 않는다.

## 검증 근거

- `npm run live:test`: 60개 통과. 기존 56개와 표시 상태 구분 테스트 4개. 초기 제한된 실행 환경에서 로컬 체인 연결 실패가 있었고, 로컬 연결을 허용한 실행으로 전체 통과했다.

- 01–05 화면, 세로 파일 입력, 기존 요청·응답 경로, 조회 후 유지되는 결과를 확인했다. 390px 모바일에서 문서 가로 넘침 없이 재배치됨을 확인했다.
- 계약·발급 데이터·PDF 원본·신뢰 설정·실제 검증 절차는 변경하지 않았다. 새 지갑 승인이나 등록 거래를 실행하지 않았다.

## 후속 개선 · 설명 추가에서 처리 연결로

사용자가 여덟 원칙을 다시 확인한 뒤 요청한 두 번째 개선이다. 내용의 기준은 동일하며, 이번에는 01–03의 시각적 처리 연결을 바꾸었다.

- 01: 가상 수탁정보에서 PDF가 만들어지는 한 동작에 집중했다. 반복되던 상단 문서 정보와 설명을 덜고, 기준시점·발급시각·문서 ID는 실제 쓰이는 문서에 남겼다.
- 02: 브라우저와 시험 발급자의 MetaMask를 공간으로 구분했다. PDF → SHA-256 해시 → EIP-712 문서 정보 → 서명 요청 → 서명값 반환을 같은 화면에서 이어 보인다. 결과와 설명은 계속 남고, 움직임만 5초 이내에 끝난다. 재생은 지갑이나 RPC를 호출하지 않는다.
- 03: 서명한 정보가 Ethereum으로 들어가 등록 기준이 되는 흐름과, 체인 밖의 PDF에 검증정보 JSON을 더해 고객사·제3자에게 전달하는 흐름을 분리했다. 실제 구현대로 JSON은 블록 포함 확인 후 다운로드할 때 구성한다. 거래 제출만 된 상태를 등록 완료로 표시하지 않으며, 자료를 제공할 수 없는 상태에는 전달 준비 전임을 표시한다.
- 04의 대시보드·세로 파일 입력·요청과 응답·세 비교 사례는 유지했다. 장면의 다음 버튼을 누르면 새 장면 처음으로 이동하도록 정리했다. 05도 기존 외부 검증 초안을 유지한다.
- 상세 구현 설명은 접힌 영역에 두었다. 동작 줄이기 설정에서는 애니메이션과 재생 버튼을 숨긴다.

후속 검증: 장면 전환·실제 결과에 따른 조회 연출·로컬 검사/최종 판정 구분의 13개 회귀 테스트 통과. TypeScript 검사와 배포 빌드 통과(기존 큰 번들 경고 유지). 브라우저의 실제 Sepolia 조회에서 원본 일치, PDF 변경본 불일치, 재서명본의 서명·파일 일치와 등록 원본 불일치를 다시 확인했다. 이때 finalized 기준 블록은 12085408이었다. 390px 화면의 02·03은 가로 넘침 없이 표시되며, 다음 버튼으로 장면을 바꾼 뒤 스크롤이 처음으로 돌아온다.

추가 스크린샷은 `processing-flow/`에 모았다. 이번에도 PDF 바이트·발급서명·계약·신뢰 기준은 변경하지 않았고 새 등록 거래나 GitHub Pages 게시를 하지 않았다. 발표용 재생을 다시 실행하는 것과 실제 발급·등록은 별개다.

# 제3자 검증을 중심으로 다시 나눈 일곱 장면

## 변경의 출발점

사용자는 발급 측 해시·서명·컨트랙트는 각각 한 장면인데, 핵심인 검증은 한 화면의 체크리스트에 압축돼 있다고 지적했다. 기존 3.5초 기록 재생은 읽을 시간을 확보했지만 설명의 비중과 장면 구분 기준을 바꾸지는 못했다. 기술 이름에 따라 준비 과정을 나누고 화면 하나에 검증 전체를 묶었던 불일치를 바로잡는 작업이다.

사용자가 승인한 기준은 ‘청중이 이해해야 할 질문과 그 답이 나오는 과정’이다. 대표님이 제시한 원본 발급→서명·해시→블록체인 기록→제3자 대조 흐름을 유지하면서, 발표의 중심을 마지막 검증에 둔다.

## 장면 구성

| 장면 | 질문과 내용 | 표현 |
| --- | --- | --- |
| 1. 수탁과 증명서 | 누구의 어떤 자산에 대한 증명서인가 | 고객사 BTC·KODA 수탁 관계, 잔고 기준시점과 발급시각 |
| 2. 검증정보 생성 | 원본을 어떤 기준으로 식별하는가 | PDF 전체 바이트→SHA-256→ID·해시·발급시각의 EIP-712 서명 |
| 3. 등록과 확정 | 외부에 남겨둘 대조 기준은 무엇인가 | register 권한·서명·최초 등록 검사, 상태 저장, 포함·확정 구분 |
| 4. 검증 시작 | 제3자는 어디에서 무엇을 제출하는가 | KODA 대시보드의 제안 검증 화면, 제출 PDF, 사전 제공 검증정보 |
| 5. 제출 문서 확인 | 파일과 발급서명에서 무엇을 계산하는가 | 제출 파일 SHA-256과 원본 검증정보 서명자 복구를 별도 경로로 표현 |
| 6. 블록체인 조회 | 발급 당시 등록된 기준을 어떻게 읽는가 | JSON-RPC 요청·Ethereum 상태·조회 응답, 동일 확정 블록의 기록 |
| 7. 대조와 결과 | 제출본이 발급 원본과 일치하는가 | 세 해시 대조, 큰 최종 판정과 대표님 세 질문 |

4~7에서 대시보드는 같은 컴포넌트와 입력 상태를 유지한다. 발표 장면 이동은 서비스 사용자의 페이지 이동을 뜻하지 않는다. 실제 검증의 함수 순서를 바꾸지 않으며 배포 검증→로컬 계산·서명 확인→공개 기록 조회→최종 대조를 실제 trace에 맞춰 표시한다.

검증이 끝나면 결과를 즉시 보여주고, 관측한 다섯 처리 그룹을 3.5초씩 다시 설명한다. 재생이 새 조회처럼 보이지 않도록 별도 표시하며 실제 실행하지 않은 단계를 재생하지 않는다. 수동 이동은 자동 설명을 중단한다.

## 지켜야 하는 기술적 구분

- 고객사 귀속 BTC는 KODA가 Bitcoin 네트워크의 고객사별 전용 지갑으로 수탁·관리한다. 대표님 제공 답변을 근거로 한 정적인 업무 배경이다. 이번 데모가 Bitcoin 잔고를 조회하거나 준비금을 증명하는 것은 아니다.
- Ethereum은 문서 검증정보를 기록하는 곳이다. BTC를 Ethereum으로 옮기는 화살표나 랩드 BTC를 추가하지 않는다.
- PDF 해시 계산과 원본 검증정보의 서명자 복구는 별도 연산이다. 제출본 해시를 원본 서명 복구 입력으로 바꿔 넣지 않는다.
- 기록 조회는 read이며 등록 거래를 다시 만들지 않는다. 확정 블록을 먼저 조회하고 그 블록 번호로 발급자·문서 기록을 읽는 현 구현을 유지한다.
- 변경본에서도 원본 검증정보의 서명은 유효할 수 있다. 서명 확인 하나로 제출 PDF의 발급 출처가 확인됐다고 표시하지 않는다.
- 원본 일치·불일치와 조회 불가·확정 대기를 구분한다. 영수증이 없는 대기 상태에서 ‘등록 완료’ 또는 ‘블록 포함 완료’를 주장하지 않는다.
- 원본과 현재 제출본의 차이를 확인하며 중간 수정·복원 이력, 현재 유효성, 공식 KODA 신원, 실제 BTC 잔고의 사실성을 증명한다고 주장하지 않는다.

## 블록체인 사용 이유와 Ethereum 선택 이유

‘블록체인에 발급 기록을 남기는 이유’는 제3자가 공개된 기준을 조회해 제출 문서와 대조할 경로를 만드는 것이다. 이는 Ethereum만의 기능이라고 설명하지 않는다.

기획상 Ethereum L1을 선택한 이유는 공개 L1에서 발급자 제한·최초 등록 보존 규칙을 EVM 컨트랙트로 실행하고 같은 확정 상태를 조회하는 구성을 택했기 때문이다. 다른 EVM 체인에서도 유사하게 구현할 수 있고, 실제 발급량·비용·허용 대기시간을 비교해 최적임을 입증한 것은 아니다. 실행은 Sepolia에서 수행한다.

근거: [Ethereum 읽기·쓰기](https://ethereum.org/developers/docs/smart-contracts/interacting/), [JSON-RPC](https://ethereum.org/developers/docs/apis/json-rpc/), [EIP-712](https://eips.ethereum.org/EIPS/eip-712), 프로젝트 내 대표님 답변과 수정 기획서. Figma 자료 작업은 중단 상태를 유지하며 Hyperliquid의 특정 화면을 확인하거나 모방했다고 기록하지 않는다.

## 개인 기여와 구현 범위

신기호는 화면별 설명 비중의 불균형과 장면 기준의 혼재, 블록체인 조회의 체크리스트화, 체인 선택 근거의 혼동, 제3자 대시보드와 결과 표현의 약점을 구체적으로 지적하고 재설계를 승인했다. AI는 이 기준을 장면·상태 전환·관측 데이터의 시각화·시험 코드로 구현했다. 새 서비스 업무나 증명 범위를 임의로 확장하는 작업이 아니다.

컨트랙트·발급 데이터·서명·핵심 검증 함수를 유지한다. 새로운 지갑 승인이나 트랜잭션은 필요하지 않으며 청중 이해도 개선의 실측 결과는 아직 없다.

## 검증 결과

- live 테스트 39/39, 웹 TypeScript와 배포용 빌드 통과. 기존 단일 번들 500 kB 경고는 남는다.
- 실제 Sepolia RPC에서 원본 `match`, 변경본 `file-mismatch` 확인. 변경본의 원본 서명은 유효하더라도 제출 파일의 발급 출처가 확인됐다고 표시하지 않는다.
- 검증 네 장면을 전환해도 대시보드 DOM과 입력이 유지된다. 실제 결과를 먼저 표시하고 관측된 기록만 3.5초씩 재생하며 재생 중 RPC 요청 수는 증가하지 않는다.
- 일시정지·수동 선택·마지막 단계 종료·파일 교체·재검증·장면 이동, 동작 줄이기와 키보드 조작을 확인했다.
- 의도적으로 조회 오류를 주입했을 때 검증 미완료와 시도한 한 단계만 표시한다. 대기 상태는 영수증 유무에 따라 블록 포함 대기와 최종 확정 대기로 구분한다.
- 1440px·1280px·390px의 일곱 장면에서 페이지 가로 넘침과 브라우저 예외가 없었다. 화면 검토 후 결과를 대시보드 상단에 우선 배치하고 기술 캔버스와 제품 UI 경계를 분리했다.

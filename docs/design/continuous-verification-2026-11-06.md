# 검증 버튼에서 판정까지 이어지는 한 동작

2026-11-06. 사용자가 두 장면 구성은 유지하되, 제3자의 조회가 구조도 설명처럼 보인다고 지적했다. 핵심 개선은 검증 버튼 → Ethereum 요청 → 등록 기록 응답 → PDF 대조의 연속성이다. 팀장 피드백의 새 비교 사례와 파일 전달·외부 업로드는 이번 범위에 넣지 않는다. 기술의 상세 설명은 기존 부록을 유지한다.

## 사용자의 의도와 설계 변경

사용자는 단순히 기술 명칭이나 해시를 더 보여 달라고 한 것이 아니다. 누가 어디에 요청하고, 무엇이 돌아오며, 그것이 검증 결과의 근거가 되는지를 하나의 사건으로 보이게 하려 했다. 결과가 먼저 나타난 뒤 세 단계 설명을 되감던 방식은 이 목적과 맞지 않았다.

- 제3자가 사용하는 KODA 대시보드를 유지하고, 옆에 중복해서 그리던 PDF 도형을 삭제했다.
- 대시보드 검증 버튼에서 문서 ID 조회 요청이 Ethereum으로 이동한다.
- 기존 블록의 등록 기록을 강조한다. 조회는 읽기 작업이므로 새 블록이나 거래가 생기지 않는다.
- 실제 읽은 원본 해시가 응답 카드로 대시보드의 대조 칸에 돌아온다. 제출 PDF의 해시와 나란히 놓인 후 일치·불일치 판정과 대표님의 세 질문을 표시한다.
- 왼쪽 지도도 조회 → 응답 → 제3자의 대조 순서와 동기화한다. BTC 수탁 관계와 Ethereum 문서 기록의 역할을 유지한다.

## 실제 처리와 연출의 경계

`prepare → request → record → return → compare → result`는 발표용 표현 순서다. 등록 컨트랙트, 서명 알고리즘, 신뢰 기준, PDF 바이트, 실제 검증 함수는 변경하지 않았다.

- request는 실제 `record` trace가 관측된 후만 가능하다. 사전 배포·거래·확정 상태 조회를 문서 ID 조회로 잘못 표시하지 않는다.
- 응답에는 `record/success`, 유효한 체인 기록, 관측된 `chainHash`가 필요하다. 시간만 지났다고 기록을 만들지 않는다.
- 비교는 실제 `hash-comparison` 실행을 요구한다. 변경본도 정상적으로 조회한 원본 기준을 받은 후 불일치한다.
- RPC 실패·서명 오류·미등록·확정 대기는 실제 확인한 범위에서 종료한다. 검증 불가를 위변조 판정으로 바꾸지 않는다.
- 실제 결과가 먼저 끝나면 작은 상태 문구로 즉시 알리고 결과 바로 보기를 제공한다. 화면의 이동 시간은 네트워크 소요 시간이 아니다.
- 일시정지는 이동 카드·블록 강조·도착 효과와 상태 전이를 멈춘다. 명시적 다시 보기는 관측한 결과를 재사용하며 추가 RPC를 발생시키지 않는다.
- 파일 교체·장면 이동은 연출을 취소한다. reduced motion은 실제 결과를 바로 보여주며 설정을 다시 켜거나 꺼도 과거 실행이 자동 재생되지 않는다.
- 모바일은 결과와 설명을 유지한다. 공간을 가로지르는 카드 이동은 데스크톱 발표 화면에 제공한다.

## 검증과 기록

컨트랙트 포함 회귀 테스트 41개 통과. TypeScript와 프로덕션 빌드 통과. 실제 Sepolia 원본 일치·변경본 불일치, 지연된 조회, 오류, 재생 중 추가 RPC 없음, 상태 취소, 키보드, reduced motion, 1440/1280/390px 브라우저 검증도 통과했다. 상세 결과는 [브라우저 검증 기록](continuous-verification-2026-11-06/browser-check.json)에 남긴다. 기존 단일 번들의 크기 경고는 남는다.

사용자의 기여: 기술 구현의 정확성과 별개로 청중이 제안의 작동을 이해할 수 있어야 한다는 문제를 짚고, 전달·조회 연속 동작을 중심, 추가 비교 사례를 보조로 정했다. AI는 이 기준에 맞춰 화면 구성, 상태 전이, 이동 연출과 검증을 구현했다. 기능 검증 통과를 디자인 만족이나 청중 이해도 검증으로 간주하지 않는다.

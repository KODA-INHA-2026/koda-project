# BTC 잔고 증명서 — 전체 기술 시연 기준

2026-11-06 사용자 피드백을 반영한 기준이다. 디자인은 아래 내용을 표현한다. 기술을 쉬운 문구로 대체하거나 중요한 값을 접어서 숨기지 않는다. KODA·고객사·제3자는 업무 주체이며 Ethereum은 등록과 조회 양쪽에서 사용하는 공통 인프라다.

## 장면과 실제 처리의 연결

| 장면 | 업무 주체·실행 위치 | 화면에 드러낼 입력 → 처리 → 출력 |
| --- | --- | --- |
| 전체 흐름 | KODA / 고객사 / 제3자, 공통 Ethereum | KODA의 기존 증명서 발급 → 검증정보 생성·등록 → 고객사의 PDF 보관·제출 → 제3자의 로컬 연산·공개 기록 조회·대조. BTC는 증명서에 기재하는 자산이며 Ethereum으로 이동하지 않는다. |
| PDF 확정 | KODA 역할, 데모의 브라우저 PDF 생성기 | 법인 전체 수탁 BTC 100.00000000, 잔고 기준시점, 발급 기재시각, 문서 ID → 최종 PDF 바이트. 실제 KODA 양식이나 운영 서버 연동은 아니다. |
| 파일 해시 | KODA 역할, 브라우저 Web Crypto | 전체 PDF 바이트 → `crypto.subtle.digest('SHA-256', bytes)` → 32바이트 `documentHash`. 화면의 24바이트 헤더는 입력 일부를 표시한 것이며 전체 파일을 계산한다. |
| 문서 서명 | KODA 역할, MetaMask 시험 발급키 | `Document(bytes32 documentId, bytes32 documentHash, uint64 issuedAt)` + EIP-712 domain → Keccak-256 구조화 다이제스트 → ECDSA secp256k1 서명. `name`, `version`, `chainId`, `verifyingContract`와 서명을 표시한다. 파일 SHA-256과 서명 다이제스트를 구분한다. |
| 등록·계약 실행 | 발급자 지갑 → Ethereum Sepolia EVM | `register(id, hash, issuedAt, signature)` → 허용 발급자·0값·중복 ID·복구 서명자 검사 → `records[id] = { documentHash, issuedAt }` + `DocumentRegistered` 이벤트. 문서 서명과 등록 거래의 지갑 승인은 별개다. 서명은 공개 거래 입력에 있으며 `records` 필드에 저장하는 것은 아니다. |
| 포함·확정 | Ethereum, 조회 브라우저 | 거래 해시 → 성공 영수증·정식 블록 포함 → `finalized` 기준 확인. 발급자가 기재한 `issuedAt`, 블록 timestamp, 조회 시각을 같은 시각으로 표현하지 않는다. 재생 타이머는 합의나 확정을 일으키지 않는다. |
| 보관·제출 | KODA → 고객사 → 제3자 | 발급 원본 PDF는 고객사가 보관하고 제3자에게 제출한다는 기획을 표현한다. 실제 전달 채널은 확인되지 않았으므로 특정 메일·API·서버를 단정하지 않는다. 외부 JSON 패키지 배포는 보류이며 데모는 한 브라우저에서 역할을 전환한다. |
| 대조·판정 | 제3자 UI + 브라우저 로컬 연산 ↔ Ethereum | 선택한 PDF → SHA-256 → EIP-712 서명자 복구 → JSON-RPC의 체인·최종 확정 블록·거래·영수증·이벤트·`authorizedIssuer`·`records` 조회 → 서명 메시지와 기록 연결 확인 → 제출 해시 대조. 서비스 UI와 그 조작에 따라 발생한 기술 처리를 동시에 보여준다. |

## 실행 사실의 표현

- 기존 승인 기록: 2026-11-06 한울테크홀딩스㈜ PDF의 서명과 등록 결과를 재생한다. 이 이름을 인하테크홀딩스㈜로 바꾸면 파일 해시가 달라지므로 기존 증거를 수정하지 않는다.
- 신규 실행: 인하테크홀딩스㈜ PDF를 새로 생성·서명·등록한다. 준비된 기존 컨트랙트를 재사용하고, 문서 서명과 거래 승인은 사용자가 직접 한다.
- 제3자 검증: 재생 중에도 검증 버튼은 실제 계산과 실제 공개 RPC 읽기를 수행한다. 재생 속도나 장면 위치로 성공을 결정하지 않는다.
- 기술 처리의 `진행 중 / 완료 / 확인 실패`는 실제 함수 실행·응답에서 나온다. 응답 대기나 미확정 상태는 성공으로 바꾸지 않는다.
- 원본: 제출 해시 = 서명된 해시 = 확정된 기록 해시. 변경본: 제출 해시만 다르고 원본의 서명·기록은 유지된다. 변경본의 출처까지 유효하다고 표현하지 않는다.

## 블록체인의 역할이 보이는 지점

해시와 서명은 파일 동일성과 서명자를 확인하는 수단이다. 추가한 컨트랙트는 누가 등록할 수 있는지, 같은 ID를 덮어쓸 수 없는지를 실행하고 공개 상태로 남긴다. 제3자는 KODA 내부 DB의 판정만 받는 대신 동일한 공개 기록을 조회해 자신의 파일과 대조한다. 이것이 이 구현에서 보여줄 블록체인의 역할이며, 실제 BTC 잔고의 사실성이나 시험키의 KODA 공식 신원까지 증명하는 것은 아니다.

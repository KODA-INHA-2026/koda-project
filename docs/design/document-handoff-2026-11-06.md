# 발급 자료가 제3자의 실제 검증 입력으로 이어지는 흐름

## 이번 작업의 기준

대표님 최종 답변의 발급 → 전자서명·해시 → 체인 기록 → 외부 수신자 대조를 중심으로 팀장님의 전달 흐름 의견을 반영한다. PDF에 검증정보 JSON을 동봉하는 것은 대표님의 직접 지정이 아니라 앞서 선택한 팀의 기술 설계다. 검증 규격·코드를 묶어 다른 환경에서 실행하는 재현 패키지(보류한 2안)와 구분한다.

두 발표 장면을 유지한다. 첫 장면은 KODA가 발급·등록한 PDF와 검증정보를 고객사가 받아 제출하는 과정이며, 실제로 두 파일을 내려받을 수 있다. 둘째는 제3자가 KODA 검증 화면에서 받은 두 파일을 불러와 Ethereum 기록과 대조하는 장면이다. 고객사 제품 UI나 외부 검증 앱은 만들지 않는다. 서명된 다른 원본과 등록 기준의 충돌 사례는 기본 전달 흐름 이후의 별도 보조 시나리오다.

## 변경 범위와 검증 계획

- 현재 발급 원본 바이트와 해당 proof를 그대로 PDF·JSON으로 내보낸다. JSON은 서명·문서 ID·원본 해시·발급 기재시각·등록 거래와 조회 대상 체인을 담는다. 비밀키·원문·고객정보·RPC URL·검증 코드를 포함하지 않는다.
- 수신자 입력을 발급자 내부 상태와 분리한다. 초기 화면은 빈 입력이며 받은 PDF·JSON을 읽기 전에는 검증할 수 없다. 발표용 예시는 명시적 보조 조작으로 제공한다.
- 제출 JSON의 주소를 새 신뢰 기준으로 채택하지 않는다. 미리 신뢰한 시험 배포 목록과 비교하며, 미등록 체인·컨트랙트·잘못된 스키마를 거절한다. 이후 기존 서명·거래·확정 기록 검증을 그대로 수행한다.
- 입력 교체 시 이전 결과를 지우고, 잘못된 파일·너무 큰 파일·중복 파일·비동기 읽기 경합에서 이전 입력으로 검증하지 않도록 한다.
- 실제 다운로드 → 별도의 깨끗한 브라우저 세션에서 업로드 → 실제 RPC 원본 일치·변경본 불일치를 검사한다. 기존 연속 요청·응답·대조, 오류, 동작 줄이기, 작은 화면도 회귀 확인한다.

기능 검증과 별개로, 화면에서 고객사와 제3자의 주체 전환 및 동일한 두 파일의 전달이 이해되는지 직접 확인한다. 전달은 기존 업무를 데모 파일 다운로드·불러오기로 재현하며 실제 KODA 운영 연동·이메일 전송·계정 권한 기능을 구현했다고 주장하지 않는다.

## 구현과 검증 결과

사용자가 지적한 문제는 ‘대표님이 요청한 업무 흐름’과 ‘우리가 선택한 파일 형식’을 혼동한 데 있었다. 대표님이 JSON 동봉을 직접 지정했다고 설명하지 않는다. 보류한 2안은 별도 환경에서 실행할 검증 코드·규격 배포이며, 이번 작업은 기존 KODA 검증 화면에서 받은 파일을 입력하는 데 한정했다.

실제 PDF와 검증정보 JSON을 내려받고 별도의 깨끗한 브라우저에서 불러와 검증하도록 구현했다. 발급자 내부 proof를 수신자에게 자동 주입하던 연결을 끊었다. 처음에는 두 입력이 비어 있고, 파일이 준비된 뒤 검증 버튼을 누르면 기존의 요청 → Ethereum 기록 → 응답 → PDF 대조 → 결과 동작이 이어진다. 발표용 원본·변경본 단축 입력은 닫힌 보조 메뉴에 두었다.

검증 JSON은 문서 ID·원본 SHA-256·발급 기재시각·EIP-712 발급서명·등록 거래 해시와 체인/계약 식별값을 담는다. v1의 등록 거래 해시는 필수이며 제거해서 거래 검사를 건너뛸 수 없다. 수신자가 신뢰할 계약과 발급자는 화면 코드에 사전 설정된 공개 실증 배포 정보로 정한다. 첨부 파일이나 발급자 브라우저의 localStorage가 새 신뢰 대상을 추가하지 못한다.

자료 받기는 성공한 등록 거래의 블록 포함이 확인된 경우에 열며, 최종 확정은 제3자 검증에서 별도로 조회한다. 최근 발급 자료를 복원할 때에는 배포정보 전체를 공개 신뢰 기준과 대조하고, 기존 검증기로 서명·등록 거래 입력·영수증·이벤트·확정 기록·PDF를 다시 검사한 뒤 전달을 허용한다. 새 시험 계약은 검증 화면의 고정 신뢰 목록에 별도로 반영하기 전에는 공유 대상이 되지 않는다. 현재 공유된 계약에서 새 문서를 발급하는 것은 같은 신뢰 기준을 사용한다.

- `npm run live:test`: **47/47 통과**. 계약 규칙, 서명·거래·최종 확정 검사, JSON 형식 및 신뢰 경계 포함.
- `npm run live:build:pages`: TypeScript·공유 경로 빌드 통과. 기존 단일 번들 크기 경고는 남음.
- `node scripts/live/check-presentation.mjs`: 실제 다운로드 파일의 해시 보존, 새 BrowserContext 빈 입력, JSON/PDF 순차 입력, 임의 계약 거절, 늦은 파일 읽기 응답 무시, 실제 RPC 원본 일치·변경본 불일치 확인. 요청·응답 연출, 일시정지·다시 보기·입력 교체, 오류·동작 줄이기, 1440/1280/390px 회귀 통과.
- `npx tsx scripts/live/check-handoff-boundaries.ts`: 미포함·실패 거래, 성공했지만 문서와 무관한 거래, 변조된 발급자 정보의 다운로드 차단을 확인. 발급자 localStorage로 수신자 신뢰 목록을 바꿀 수 없음도 확인.
- 브라우저 예외 및 새 지갑 승인·서명·거래 요청 없음. 이미 승인한 실증 원본을 그대로 사용했다.

한눈에 보는 전달 구조를 유지하면서 실제 수신 입력을 추가했다. 제3자의 대시보드만 제품 화면으로 보이며, 발급·등록·고객사 전달은 기술과 업무의 흐름으로 표현했다. 정상 원본·변경본의 기술적 판정을 검사했으며, 실제 KODA 운영 연동이나 청중 이해도 측정까지 완료했다는 의미는 아니다.

## 기여 기록

신기호는 대표님 최종 답변을 솔루션의 기준으로 유지하고, 팀장 피드백 중 주체 전환과 전달의 연속성을 채택했다. 외부 재현 패키지와 증빙 동봉 정보를 구분하도록 요구했으며, ‘그림 속 전달’이 실제 내려받기·불러오기·검증으로 이어지게 데모 범위를 구체화했다. 이번 구현은 그 판단을 수신자 입력 격리, 발급 기록의 신뢰 기준, 실제 파일·체인 조회 증거로 연결한 작업이다.

서명된 다른 원본과 동일 문서 ID의 등록 원본이 충돌하는 비교 사례는 별도 보조 시나리오로 남긴다. 그 사례는 새로운 유효한 발급서명이 있어야 하며, 현재의 단순 120 BTC 변경본과 동일하게 취급하지 않는다.

# 조회 버튼 뒤 실제 코드와 블록체인 동작

## 문제의식과 사용자 기여

신기호는 기존 데모의 정보 이동 화살표만으로는 무엇을 구현했는지 확인하기 어렵다고 지적했다. 제3자가 검증 버튼을 누를 때 어떤 코드와 컨트랙트가 실행되고, 어디에서 결과를 읽는지 보여 달라고 요청했다. 기술 이름을 나열하는 데 그치지 않고 서비스 동작과 실제 구현의 연결을 보이는 것이 이번 개선의 목적이다.

기존 원칙은 유지한다. 대표님 답변에 따른 발급·전달·대조 흐름, KODA·고객사·제3자의 역할, 제3자에게만 서비스 UI를 보여 주는 구성, BTC 자산과 Ethereum 문서 기록의 구분이 기준이다. 새 기술이나 별도 검증 규칙을 추가하는 작업이 아니다.

## 반영 범위

- 02의 제품 화면 밖에 짧은 실행 코드 영역을 둔다. 브라우저 검증 코드 → viem → JSON-RPC → DocumentRegistry → 응답 해석 → PDF 대조를 기존 연속 동작에 맞춰 보여 준다.
- 발표 연출 단계와 실제 실행 상태를 구분한다. 실제 호출이 끝난 뒤의 설명 연출이나 다시 보기를 추가 RPC 실행으로 표현하지 않는다.
- 지갑 연결 등 다른 작업의 busy 상태가 검증 실행으로 보이는 문제를 수정한다.
- 기술 부록에는 viem의 두 클라이언트, `eth_call`의 의미, 문서 서명과 등록 거래의 차이, 지갑·가스비 부담 주체를 실제 소스와 공식 문서에 연결한다.

## 지갑과 비용

| 동작 | 실행 위치·방식 | 지갑 승인 | 체인 거래 수수료 |
|---|---|---|---|
| PDF SHA-256·서명 복구 | 제3자 브라우저 | 없음 | 없음 |
| EIP-712 문서 서명 | 발급자의 키·지갑 | 필요 | 없음 |
| `register(...)` | 발급자가 전송한 쓰기 거래 | 필요 | 현재 구조에서는 발급자 계정이 부담 |
| `records(documentId)` 조회 | RPC 노드가 해당 블록 상태에서 `eth_call` 실행 | 없음 | 없음 |

RPC는 요청 전달 방식이며 읽기 전용의 동의어가 아니다. 트랜잭션 전송도 RPC를 이용한다. `eth_call`에는 실행 자원 제한이 있을 수 있지만 이 호출 자체의 온체인 수수료를 내는 것은 아니다. RPC 서비스의 요금·사용량 제한은 별도다.

## 실제 등록 증거

사용자가 기존 계약에 인하테크홀딩스㈜ 증명서를 새로 등록하도록 승인했다. 자동 브라우저 제어는 현재 주소를 확인하지 못해 연결 요청 이후 중단됐고, 사용자가 직접 승인 완료를 알렸다. 거래 해시·성공 영수증·등록값·PDF 해시·finalized 상태를 확인하기 전에는 새 등록 성공이나 새 파일의 원본 검증을 확정하지 않는다. 기존 실증 데이터는 그대로 보존한다.

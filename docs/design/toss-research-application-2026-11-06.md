## 구현 전 계획

1. 구조도: ‘공개 검증 인프라’, ‘고객 BTC가 올라가는 체인이 아님’을 Ethereum의 구체적인 역할 설명으로 통합한다. 주체·PDF 전달·등록·조회 경로를 유지한다.
2. 8개 장면: 제목은 주체와 행동, 설명은 입력·결과·다음 단계의 관계로 작성한다. 내부 구현 메모는 해당 기술 상세에 둔다. 번호는 하단 1~8 체계로 통일한다.
3. 제3자 화면: 사전 제공된 검증정보를 명시하고, 제품 UI의 세 질문을 보존한다. 기술 영역에는 실제 선행 배포 확인, SHA-256, ECDSA 주소 복구, Ethereum 조회, 세 해시 대조를 보여준다.
4. 상태: 실제 trace에서 진행·완료·실패를 읽는다. 조회가 실패한 경우 완료로 보이지 않게 하며, 네트워크 응답 시간을 인위적으로 늘리지 않는다. 원본 일치와 변경 여부는 같은 파일 대조의 두 질문임을 설명한다.
5. 검증: 기존 live 단위/컨트랙트 테스트로 기술 동작을 확인하고, TypeScript·빌드·브라우저에서 전체 장면, 원본/변경본, 실패·대기 표현, 모바일·키보드·reduced motion을 확인한다. 승인 없이 새 거래를 제출하지 않는다.

기술 처리 함수·지갑·기등록 PDF·컨트랙트는 이번 표현 수정의 대상이 아니다. 새 의존성은 추가하지 않는다. 상세 검증 결과와 화면 경로는 완료 후 아래에 기록한다.

## 반영·검증 결과

### 반영한 내용

- 전체 8장면의 제목·설명·연결 문구를 주체와 행동 중심으로 수정했다. 장면 번호는 하단 1~8만 사용한다.
- Ethereum 역할을 ‘KODA가 발급한 문서의 검증정보를 기록합니다’로 정리했다. KODA·고객사·제3자, 등록·조회 경로와 기존 색상을 유지했다.
- 첫 장면에 대표님 답변의 세 질문을 명시했다. 제3자 제품 화면에서도 세 질문을 유지하고 시험 발급자·현재 파일 비교의 범위를 붙였다.
- 제품 버튼은 ‘문서 검증하기’, 기술 영역은 ‘검증 과정’으로 구분했다. 사전에 불러온 문서 검증정보를 사용한다는 조건을 표시했다.
- 실제 trace를 배포 확인→SHA-256→서명자 복구→확정 기록 조회→세 해시 대조로 묶었다. 로컬 연산과 Ethereum 호출을 구분하고, 전체 호출 로그와 전체 값을 펼쳐 볼 수 있게 유지했다.
- 기존 두 해시 표시를 제출본·서명 데이터·체인 기록의 세 해시 표시로 바꿨다. 같은 PDF가 서명과 조회까지 이어지는 관계를 드러낸다.
- 검토 중 발견한 오류 표현도 수정했다. `unavailable`을 무조건 RPC 실패로 부르지 않고 실제 실패 trace에 따라 로컬 계산·컨트랙트 확인·체인 조회 실패를 구분한다.

### 검증 증거

- `npm run live:test`: **30/30 통과**. 기존 26개에 표시 상태와 오류 위치 회귀 테스트 4개를 더했다. 샌드박스 안의 첫 실행은 로컬 Hardhat 서버 연결 제한으로 4개가 시간 초과됐고, 동일 테스트를 로컬 네트워크 접근이 가능한 실행에서 모두 통과했다.
- `npm run live:build:pages`: TypeScript 검사와 프로덕션 빌드 통과. 기존 단일 JS 번들 500 kB 초과 경고는 남아 있다.
- `node scripts/live/check-presentation.mjs`: 8개 장면 이동, 실제 Sepolia 원본 일치·120 BTC 변경본 불일치, 실패 후 재시도 동작을 확인했다. 두 조회는 새 서명·거래 없이 수행했다.
- RPC 오류 화면은 테스트가 의도적으로 응답 실패를 주입해 확인한 것이다. 실제 서비스 장애로 기록하지 않는다. 최종 확정 대기와 로컬 해시 실패 분류는 단위 테스트로 검증했으며, 이번에 새 거래로 확정 대기를 재현하지 않았다.
- 1440px 데스크톱, 1280px·390px에서 모든 장면의 가로 넘침 없음. 키보드로 장면 선택, reduced motion에서 자동 재생 비활성 확인. 브라우저 page error 없음.

# 02의 재서명 비교 사례

사용자 요청: 팀장 발표 흐름을 살리되 기존 발급·전달 → 제3자 검증 서비스와 두 장면 구성을 유지한다.

## 이번 변경

- 01 발급·전달, 전체 구조도, 03 외부 검증의 기존 동작은 유지한다.
- 02의 발표용 자료 선택에 원본 / PDF만 변경 / 다시 서명한 문서를 제공한다. 같은 입력창·검증 버튼·Ethereum 조회·응답·결과 영역을 재사용한다.
- 재서명 비교에서만 제출 파일에 대한 로컬 서명·해시 검사를 짧게 표시한다. 결과는 등록 기준과의 불일치를 설명하며 대표님 세 질문은 유지한다.
- 기존 등록 원본의 거래·영수증·이벤트·확정 상태 검사는 생략하지 않는다. 별도 서명 메시지와 등록된 원본의 검증정보를 분리한다.
- 비교용 서명은 실제 시험 발급자 지갑으로 만든다. 승인이 없으면 준비 전으로 표시하며 성공을 만들어내지 않는다. 새 등록 거래를 보내지 않는다.
- 발표자 준비 도구에서 서명·검증정보 가져오기/내려받기를 지원하고, 제3자 화면에는 지갑을 요구하지 않는다.

## 검증 기준

정상/단순 변경본 기존 회귀, 유효한 재서명과 등록 기준 불일치, 잘못된 서명·문서 ID·등록 거래 거절, 조회 실패·확정 대기 유지, 화면 전환 시 결과 초기화, 실제 RPC 요청/응답 표시, 모바일·일시정지·동작 줄이기를 확인한다.

## 설명 범위

같은 발급자가 같은 문서 ID의 다른 내용을 다시 서명했다는 비교 가정이다. 실제 KODA 사고나 일반 수신자의 서명 위조를 의미하지 않는다. 서명 유효성과 등록 원본의 일치를 구분한다. 블록체인의 가치는 기관 내부 DB와 분리된 공동 조회 기준이며, 문서 내용의 사실성이나 현재 유효성을 자동 보증하지 않는다.

## 실제 서명과 확인

사용자가 2026-11-07 직접 MetaMask 메시지 서명을 승인하고 비교정보 JSON을 내려받았다. 개인키를 받거나 새 등록 거래를 보내지 않았다. 실제 시험 발급자의 서명을 복구하고 PDF 전체 해시와 대조했으며, 기존 등록 거래·영수증·이벤트·정식 블록·finality·허용 발급자·저장값을 기존 검증기로 모두 확인했다.

- 비교 PDF / 새 서명 해시: `0x42c75760d2ffded3f5ead8c19a5c7d83b20bc6d722f8b5236ac570cbe3df546e`
- 기존 등록 해시: `0xba9bca0bd4723155b7084a54a3bb0f41bb235b94bc4ea44fa331bc94f6579f3c`
- 같은 문서 ID: `0xdada759a9083cf2925597621c83e530e62625c56d4fbd31c1874e43926f019fe`
- 관측 결과: 새 서명 유효 / PDF와 새 서명 일치 / 확정 등록 원본과 불일치.
- 최초 보존 조회 기준: finalized 블록 `12077483`. 시연 버튼은 새로 조회한다.

비교용 JSON은 `koda-signed-comparison-v1`이며 새 서명 메시지와 기존 등록 거래의 참조를 구분한다. 새 서명에 기존 거래를 붙여 등록된 것처럼 표현하지 않는다. 보조 사례는 같은 문서 ID·발급 기재시각에서 PDF만 달리한 상황으로 한정한다. 03 외부 실행 패키지는 기존 원본·단순 변경본의 일반 검증을 유지하며 이 비교 전용 포맷은 02에서 사용한다.

## 확인한 동작

54개 live 테스트 통과. 로컬 테스트 체인은 일반 실행 환경에서 시작되지 않아 허용된 별도 실행으로 재검사했고 모두 통과했다. TypeScript·공유 빌드 통과(기존 번들 크기 경고 유지). 독립 브라우저에서 실제 RPC로 정상본·단순 변경본·재서명본을 검증했다. 비교 JSON과 PDF를 각각 불러오는 전달 경로, 파일 선택 시 기존 결과 초기화, 비교 단계 일시정지, 요청·응답 경로, 조회 장애 시 이전 결과 제거, 1440/1280/390px 배치, 01·03 회귀도 확인했다.

기록: [실제 서명과 검증](../portfolio/2026-11-07-signed-comparison/verification.json), [브라우저 관측](signed-comparison-2026-11-07/browser-check.json).

[공개 HTTPS 검수](signed-comparison-2026-11-07/public-check.json)에서도 세 사례·각 파일 따로 불러오기·RPC 실패·모바일·01/03 회귀를 확인했다. 파일을 따로 선택하는 자동 검사에서는 첫 PDF 읽기 완료를 기다린 뒤 JSON을 선택하도록 검사 순서를 맞췄다.

## 발표 순서

01의 발급·등록·고객사 전달 후 02에서 받은 파일을 검증한다. 정상 확인을 먼저 보여주고, 필요하면 ‘PDF만 변경’으로 파일 무결성을 설명한다. 이후 ‘다시 서명한 문서’를 선택해 같은 검증 버튼을 누른다. 브라우저의 서명·PDF 검사 두 개가 통과하고, Ethereum에서 돌아온 등록 해시와 다른 결과를 설명한다. 결과 화면은 그대로 유지하며 새 장면이나 새로운 업무 주체를 추가하지 않는다.

## 기여 기록

신기호는 팀장 발표 흐름을 살리면서도 대표님이 정한 문서 검증 서비스의 중심과 전체 구성이 흔들리지 않아야 한다고 요구했다. 이에 보조 사례를 02의 동일 화면 안에 제한하고, 암호학적 서명의 유효성과 공개 등록 기준의 일치를 구분했다. 신기호가 실제 시험 발급자 서명을 승인했고, AI는 비교 검증·자료 전달·연출·회귀 검사를 구현했다. 이 작업의 성과는 단순 PDF 변경 탐지에 머물던 시연에서 공개 등록 기준이 추가하는 판단을 실제 결과로 보여준 것이다.

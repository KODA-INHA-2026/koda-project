## 왜 블록체인인가: 현재 사례와 보조 사례

현재 변경본은 기존 JSON·서명을 유지하고 PDF만 바꾼다. 원본 메시지의 서명은 유효하지만 제출 PDF의 SHA-256이 그 메시지에 들어 있는 해시와 다르다. 올바른 전자서명 기반 문서 검사만으로도 탐지할 수 있으므로 이 사례를 블록체인만의 성과로 설명하면 안 된다.

팀장 의견은 변경 PDF의 해시에 대해 신뢰 발급자가 같은 문서 ID로 다시 서명한 경우다. 이때 파일과 새 서명은 서로 맞지만 이미 등록된 최초 원본과는 다르다. 발급자 키를 가진 주체의 재서명이라는 전제가 필요하며 일반 외부 공격자가 서명을 위조한 사례가 아니다.

현재 수신 JSON은 등록 거래 해시가 필수다. 새 서명·해시에 기존 거래 해시를 붙이면 `verification.ts`의 거래 입력 대조에서 먼저 `invalid`로 종료하며 `records` 조회까지 가지 않는다. 거래 해시를 지운 JSON은 파서가 거절한다. 따라서 보조 사례를 구현할 때 필수 검사를 빼면 안 된다. 파일·서명의 자체 일치와 기존 등록 기준과의 불일치를 각각 보여주는 비교 경로를 추가로 설계해야 한다. 새 오프체인 서명에는 사용자 지갑 승인이 필요하지만 새 온체인 거래는 필요 없다.

블록체인이 추가하는 것은 발급기관 DB와 분리된 공통 등록 기준과 외부 조회 경로다. 중복 ID 거절 규칙은 중앙 DB에도 구현할 수 있다. Ethereum을 썼다는 이유만으로 입력 정보의 진실성, 공식 KODA 신원, 무신뢰 RPC 검증까지 확보했다고 주장하지 않는다.

## 지금부터의 순서

1. 새 등록의 finalized 상태를 확인하고 새 원본·변경본을 실제 검증한다. 화면은 마지막 검사 결과를 유지하므로 확정 후 검증을 다시 실행한다. 재발급하지 않는다.
2. 새 인하테크홀딩스 파일을 공개 데모 기본 자료와 03 패키지에 함께 반영하고 다시 검수한다. 기존 한울 원본과 서명·거래 기록은 역사적 증거로 보존한다.
3. 01에 가상 수탁 원천정보에서 PDF로 이어지는 연결을 보강한다. 01·02의 큰 장면 구분, 제3자 중심 UI, 고정된 요청·응답 설명을 유지한다.
4. 핵심 흐름을 유지한 채 팀장 제안의 재서명 비교 사례를 보조 시나리오로 준비한다. 단순 변경본과 구분하고, 현재 미구현임을 명시한다.
5. 한 명이 발급 자료를 고객사 역할로 내려받아 제출하고, 수신자 역할로 불러와 검증하는 리허설·녹화를 한다. 이미 확정된 거래와 현장에서 수행하는 새 조회를 구분한다.

## KODA와 확인할 운영 조건

- 외부 수신자의 대시보드 접근·초대·로그인·권한 정책. 대표님은 외부 검증의 가치를 설명했지만 무로그인을 확정하지 않았다.
- 공식 발급자 주소와 계약을 신뢰 목록에 등록·배포하는 방법, 키 교체·정정·폐기 정책.
- 실제 증명서 양식, 원천정보 추출 방식, 운영 RPC·비용·유지 주체.

권한 관리 전체, 마스킹 검증, BTC 실재·소유권·준비금·이중담보 증명은 현재 문서 검증 데모의 구현 항목으로 임의 추가하지 않는다. 대표님은 통합금고를 이번 범위에서 제외했고, CTO의 BIP-340·머클·ZK는 리서치 예시였다.

## 왜 배포했는데 발급 버튼이 비활성이었나

처음 관측한 2026-11-06 03:39:43 KST에는 배포 블록이 **12071288**, 최신 블록이 **12071313**, finalized 블록이 **12071228**이었다. 배포는 성공했지만 배포 블록이 확정된 범위보다 뒤에 있었다.

이 프로젝트는 **계약의 코드·발급자·배포 거래를 확인하고 배포 블록의 최종 확정까지 확인한 다음 문서 서명·등록을 활성화**하는 보수적인 실행 기준을 선택했다. Ethereum 자체가 모든 계약 호출에 이 대기를 강제하는 것은 아니다. 이 시연에서 발급서명의 `verifyingContract`가 가리키는 배포 기준을 확정한 뒤 진행하려는 설계다.

또한 처음 UI에는 두 가지 문제가 있었다.

1. 배포 거래를 보낸 뒤에도 최종 승인 전에는 계약을 ‘배포 전’이라고 표시해 실제 성공 여부가 불명확했다.
2. 확정 상태의 재조회와 새로고침 후 지갑 연결 복원이 자동이 아니어서, 시간이 지나도 버튼이 비활성으로 보일 수 있었다.

이를 계기로 전송·포함·확정 상태와 실제 블록 번호를 표시하고, 대기 중에는 12초마다 읽기 전용 조회를 하도록 개선했다. 확정 뒤에는 전체 배포 검사를 통과해야 활성화한다. 이전에 사이트에 허용한 지갑 계정은 `eth_accounts`로 복원하며 새 지갑 권한을 자동으로 요청하지 않는다. 실제 발급 직전에는 계정·네트워크를 다시 검사한다.

## 상태를 구분하는 기준

| 상태 | 근거 | 다음 행동 |
| --- | --- | --- |
| 거래 전송 | MetaMask 승인 후 거래 해시 반환 | 같은 배포를 중복 전송하지 않고 조회 |
| 블록 포함 | 성공 영수증과 계약 주소, 정식 블록 해시 확인 | finalized 헤드와 배포 블록 비교 |
| 최종 확정 대기 | 배포 블록 > finalized 블록 | 읽기 전용 재조회; 시간만으로 완료 처리하지 않음 |
| 배포 확정 | 배포 블록 ≤ finalized 블록 + 정식 블록·코드·발급자 일치 | 시험 발급자 연결 상태에서 문서 발급·등록 가능 |
| 조회 실패 | RPC 장애·체인 불일치·정보 부족 | 위조나 성공으로 판정하지 않고 원인 확인 |

이후 문서 등록 트랜잭션도 포함과 확정을 구분한다. 정상 원본 판정은 파일 해시·발급서명·확정 기록·등록 거래의 연결이 모두 맞아야 한다. 조회는 별도 지갑 서명이나 가스 없이 수행한다.

## 증거와 재현

- `deployment-*.json`: 각 시점의 조회 결과. 시간이 지나도 앞선 대기 관측을 덮어쓰지 않는다.
- `deployment-latest.json`: 가장 최근 조회 결과.
- `scripts/live/capture-deployment.mjs`: 공개 배포 거래를 읽어 코드·발급자·블록과 수수료를 대조하고 JSON으로 저장한다. 거래를 보내지 않는 스크립트다.
- 소스 스냅샷은 현재 구현 파일과 패키지 잠금 파일을 해시 목록과 함께 보존한다. 지갑 개인키나 브라우저 저장소는 포함하지 않는다.

배포는 문서 등록과 다르다. 이후 등록 거래와 제3자 판정까지 별도로 확인했으며, 완료 근거는 [검증 기록](VERIFICATION.md)과 `registration-latest.json`에 연결했다.
